Syntax-Directed Translation & Three-Address Code

Covers semantic analysis, attribute grammars (synthesized, inherited, S- and L-attributed), SDD-driven translation, three-address code and its representations, and the exact exam question “annotate the parse tree and generate code for a := b * -c + b * -c”. Lecture slides 431–451 are the base; the exam parts follow the Dragon Book (Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools, 2nd ed.).

1. Why semantic analysis and SDT?

  • A parse tree only says the string is well formed. It carries no meaning and no instructions for evaluating anything. The productions of a CFG “do not accommodate how to interpret them” (slides). CFG + semantic rules = Syntax-Directed Definition (SDD).
  • Semantic analysis does scope resolution, type checking and array-bound checking. It must recognize: type mismatch, undeclared variable, reserved-identifier misuse, multiple declarations in one scope, out-of-scope access, and actual/formal parameter mismatch. The parser cannot detect these.
  • Syntax-directed translation attaches information to grammar symbols and computes it as the parse proceeds. Two methods: attribute grammars / SDD (rules per production; no order stated) and translation schemes (actions in { } placed inside the production body, so the order is explicit).
  • Expansion vs reduction (slides): expansion replaces a non-terminal using a rule (top-down); reduction replaces a body by its non-terminal (bottom-up). Semantic rules run at reduction in the bottom-up view.
  • Typical outputs: values (calculator), postfix strings, syntax trees, three-address code (intermediate code), type information, symbol-table updates.
Read: Dragon Book Ch. 5 “Syntax-Directed Translation” (§5.1 Syntax-Directed Definitions; §5.4 Syntax-Directed Translation Schemes); Ch. 2 §2.3 “Syntax-Directed Translation”.

2. Attributes and annotated parse trees

An attribute is a value (integer, string, type, code, memory location) attached to a grammar symbol, e.g. E.val, id.lexval (the lexical value the scanner returns), E.place, E.code. A parse tree with attribute values written at its nodes is an annotated parse tree.

SynthesizedInherited
Value comes fromChildren of the node (and the node’s own tokens)Parent and/or siblings
In S → ABCS gets values from A, B, CA may use S, B, C; B may use S, A, C; C may use S, A, B
Evaluation directionBottom-upTop-down / sideways
Typical useExpression values, code strings, postfixDeclaration types, expected types, inherited labels
Example ruleE → E₁ + T { E.val = E₁.val + T.val }L → L₁ , id { L₁.in = L.in }
Tokens only synthesize: terminals such as num or id have attributes supplied by the lexer (num.lexval, id.place/id.entry pointing into the symbol table). They never inherit.

Inherited-attribute example: declarations Dragon Book §5.1

D → T L        { L.in = T.type }
T → int        { T.type = integer }
T → float      { T.type = float }
L → L1 , id    { L1.in = L.in ; addtype(id.entry, L.in) }
L → id         { addtype(id.entry, L.in) }

For float a, b, c: T.type = float is synthesized; L.in gets it from its sibling T (inherited), passes it down the left-recursive L chain, and each id is stored with that type in the symbol table. This is how declarations in Fall 2023 Q4(a) (“variable declarations, assignments and arithmetic expressions”) get their types.

3. S-attributed vs L-attributed

S-attributedL-attributed
Allowed attributesSynthesized onlySynthesized + inherited with a restriction
Restrictionnone neededAn inherited attribute of Xᵢ in A → X₁X₂…Xₙ may use only: A’s inherited attributes, and attributes of X₁…Xᵢ₋₁ (left siblings). Never a right sibling.
Action positionRightmost, after the bodyAnywhere in the body (before a symbol if it inherits something for it)
ParsingBottom-up (evaluate at reduction)Top-down, depth-first, left to right
RelationEvery S-attributed SDD is also L-attributed.

For S → ABC under L-attribution (slides): S takes values from A, B, C (synthesized); A can use only S; B can use S and A (not C, its right sibling); C can use S, A and B.

The slide quiz, solved

Rule set 1 for A → PQ: P.i = A.i + 2, Q.i = P.i + A.i, A.s = P.s + Q.s. P uses the parent; Q uses its left sibling and the parent; A.s is synthesized. L-attributed. Rule set 2 for A → XY: X.i = A.i + Y.i needs Y, a right sibling. Not L-attributed. Answer: only 1 is L-attributed.

Checklist to classify an SDD: (1) any inherited attribute at all? No → S-attributed. (2) For every inherited attribute, list what it reads. (3) Does any read come from a symbol to its right, or form a circular dependency? Yes → not L-attributed. Otherwise L-attributed.

4. Worked SDDs

A. Desk calculator (S-attributed) slides 443–444

S → E $        { print(E.val) }
E → E1 + T     { E.val = E1.val + T.val }
E → T          { E.val = T.val }
T → T1 * F     { T.val = T1.val * F.val }
T → F          { T.val = F.val }
F → ( E )      { F.val = E.val }
F → num        { F.val = num.lexval }

Annotated tree for 3*5+4 (values in brackets): E[19] → E[15] + T[4]; E[15] → T[15] → T[3]*F[5]; T[3] → F[3] → num(3); F[5] → num(5); T[4] → F[4] → num(4). Evaluation is a post-order walk: leaves first, so parents always find their children ready.

B. Infix → postfix (S-attributed) slides 448–450

E → E1 + T     { E.val = E1.val || T.val || '+' }
E → E1 - T     { E.val = E1.val || T.val || '-' }
E → T          { E.val = T.val }
T → num        { T.val = num }

|| is string concatenation. For 3 + 2 - 4: the tree groups left to right, (3+2)-4. T[3] → E[3]; T[2]; E[3 2 +]; T[4]; E[3 2 + 4 -]. Result 3 2 + 4 -. (If the rule concatenated '+' || E1.val || T.val you would get prefix instead; the position of the operator in the rule decides the notation.)

C. Same grammar, different goal: the infix string itself

Slide 448 uses E.val = E1.val || '+' || T.val to rebuild the infix string. Comparing B and C shows the idea of SDT: one grammar, different semantic rules, different translation.

D. Why left recursion matters here

These SDDs are written on left-recursive grammars, which suits bottom-up parsing (S-attributed). A top-down parser needs the grammar rewritten (E → TE′) and then must pass the partial result down as an inherited attribute (E′.inh), giving an L-attributed SDD. Dragon Book §5.4.

5. Three-address code (TAC)

Definition: a linear intermediate representation in which each instruction has at most one operator and at most three addresses (two operands, one result). Complex expressions are broken up with compiler-generated temporaries t1, t2…. It sits between the front end and the optimizer/code generator, so it is machine-independent: one front end can drive many back ends, and the optimizer works on it once.

param x, call p, n, return yprocedure calls

Notice that quadruple rows 0–1 and 2–3 compute the same thing; common sub-expression elimination (optimization chapter) turns the code into t1 = uminus c; t2 = b * t1; t5 = t2 + t2; a = t5.

6. Exam question: SDD that generates TAC

Asked in Spring 2025, Fall 2024 and Spring 2024 (6 marks). Attributes: E.place (name holding E’s value) and E.code (the TAC sequence); newtemp returns a fresh temporary; gen(…) builds one instruction; || joins code.

S → id := E     S.code = E.code || gen(id.place ':=' E.place)
E → E1 + E2     E.place = newtemp
                E.code  = E1.code || E2.code || gen(E.place ':=' E1.place '+' E2.place)
E → E1 * E2     E.place = newtemp
                E.code  = E1.code || E2.code || gen(E.place ':=' E1.place '*' E2.place)
E → - E1        E.place = newtemp
                E.code  = E1.code || gen(E.place ':=' 'uminus' E1.place)
E → ( E1 )      E.place = E1.place ;  E.code = E1.code
E → id          E.place = id.place ;  E.code = ''

All attributes are synthesized, so the SDD is S-attributed and can run during bottom-up parsing.

Precedence (grammar from the exam, with the usual rules): unary minus > * > +. So the input is a := ((b * (-c)) + (b * (-c))):

7. Translating control flow into TAC

Control statements become labels and jumps. A common scheme: each statement S has an inherited label S.next (where to continue), and conditions B have two jump targets B.true and B.false (Dragon Book §6.6).

StatementTAC layout
if (B) S1B.code (true → Lt, false → S.next) · Lt: S1.code
if (B) S1 else S2B.code · Lt: S1.code · goto S.next · Lf: S2.code
while (B) S1Lb: B.code (true → Lt, false → S.next) · Lt: S1.code · goto Lb
for (init; cond; step) S1init · Lb: cond (false → exit) · S1 · step · goto Lb
switch (e)evaluate t = e · goto TEST · each case body ends with goto NEXT (that is break) · TEST: if t == c1 goto L1 … goto Ldefault · NEXT:

Spring 2023: while loops and switch

while (i <= end) { j = 1; while (j <= i) { j = j + 1; } i = i + 1; }
switch (b) { case 1: i--; break;  case 2: j = -i*3+5; break;  default: i = 0; }
L1:  if i > end goto EXIT1
     j = 1
L2:  if j > i goto L3
     j = j + 1
     goto L2
L3:  i = i + 1
     goto L1
EXIT1: goto TEST
C1:  i = i - 1
     goto NEXT
C2:  t1 = uminus i
     t2 = t1 * 3
     t3 = t2 + 5
     j = t3
     goto NEXT
D:   i = 0
     goto NEXT
TEST: if b == 1 goto C1
      if b == 2 goto C2
      goto D
NEXT:

-i*3+5 is ((-i)*3)+5. The condition i <= end is tested as the negation i > end so that a jump leaves the loop and the body falls through.

Fall 2023: nested for loops

for (i = 1; i <= rows; i++) {
  for (space = 1; space <= rows - i; space++) { hello++; }
  for (j = 1; j <= (2*i - 1); j++) { --hello; } }
     i = 1
L1:  if i > rows goto END
     space = 1
L2:  t1 = rows - i
     if space > t1 goto L3
     hello = hello + 1
     space = space + 1
     goto L2
L3:  j = 1
L4:  t2 = 2 * i
     t3 = t2 - 1
     if j > t3 goto L5
     hello = hello - 1
     j = j + 1
     goto L4
L5:  i = i + 1
     goto L1
END:

The bounds rows - i and 2*i - 1 are recomputed every iteration (t1 to t3 sit inside the loop) because that is what the source says. An optimizer would move them out of the loop since i does not change inside, which is why the exam answer is accepted either way when explained.

8. Common mistakes & practice

  • Forgetting that unary minus has its own temporary and own instruction (uminus).
  • Writing code in the wrong order: E1.code || E2.code must come before the instruction that uses their places.
  • Calling an SDD with a right-sibling dependency “L-attributed”.
  • Giving E.place for an identifier an empty string: the place of id is the name (or symbol-table entry), and its code is empty.
  • Mixing up quadruple rows: the result column exists only in quadruples; triples refer to a row number.
  • Jumping on the true condition instead of its negation in loops, producing wrong label layout.

Try these

P1. Annotate the tree and generate TAC for x := (a + b) * (c - d) using the exam SDD (this grammar has no - binary rule: treat c - d as c + (-d)).

Answer
t1 := a + b
t2 := uminus d
t3 := c + t2
t4 := t1 * t3
x  := t4
Parenthesized E copies place and code unchanged (E.place = E1.place), so no extra instruction is generated for the brackets.

P2. Give the postfix output of the SDD in 4.B for 9 - 5 + 2.

AnswerLeft to right grouping: (9-5)+2. E[9] → E[9 5 -] → E[9 5 - 2 +]. Postfix: 9 5 - 2 +.

P3. Is this SDD L-attributed? A → B C, rules: C.i = A.i, B.i = C.s, A.s = B.s.

AnswerNo. B.i = C.s makes the inherited attribute of B depend on a right sibling (C). An S-attributed or L-attributed SDD cannot do this.
