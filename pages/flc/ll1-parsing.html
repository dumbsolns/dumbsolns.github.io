Top-Down Parsing & LL(1)

Slides 364–428: the parser’s role, ambiguity, left factoring, left recursion, FIRST/FOLLOW, the predictive parsing table and error recovery. It also solves every LL(1) question from your five papers (Q2b, 7 marks), the “make this grammar suitable for top-down parsing” question (Q3c) and the Q1 theory questions. Textbook: Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools (Dragon Book, 2nd ed.), Ch. 4.

1. The role of the parser

  • The syntax analyzer gets tokens from the lexer, checks that the token string is generated by the grammar (a CFG), builds the parse tree/AST and reports syntax errors with recovery. It cannot catch re-declaration, use before initialization or type mismatch (semantic phase). It checks the structural correctness of the program: brackets, statement shape, operator nesting.
  • Why CFG, not regular expressions: nesting (balanced brackets, if-else) needs a stack. Every regular language is context-free, not conversely. Tokens are the terminals of the grammar; attributes stay in the symbol table.
  • Parsing algorithms: top-down (builds from the start symbol, leftmost derivation: recursive descent with backtracking, predictive/LL(1)); bottom-up (reverse rightmost derivation: LR, SLR, LALR; see the LR page). Universal methods (CYK, Earley) handle any CFG but are too slow for compilers.

2. Making a grammar suitable for top-down parsing

Top-down parsers loop forever on left recursion, cannot pick between alternatives with a shared prefix, and fail on ambiguity. So transform the grammar first slides 380–415:

A. Ambiguity

Remove by disambiguating rules (precedence, left associativity) without changing the grammar, or by rewriting with one non-terminal per precedence level: E → E+T | T; T → T*F | F; F → (E) | id (higher precedence deeper in the tree). Dangling else: match each else with the nearest unmatched then.

B. Left factoring

A → αβ₁ | αβ₂ | γ becomes A → αA′ | γ; A′ → β₁ | β₂. Example: S → iEtS | iEtSeS | a becomes S → iEtSS′ | a; S′ → eS | ε.

C. Immediate left recursion

A → Aα₁ | … | Aαₘ | β₁ | … | βₙ (no βᵢ starts with A) becomes A → β₁A′ | … | βₙA′; A′ → α₁A′ | … | αₘA′ | ε. Example: E → E+T | T becomes E → TE′; E′ → +TE′ | ε.

D. Indirect left recursion slide 410

Order the non-terminals A₁…Aₙ. For i = 1..n: for each j < i substitute the productions of Aⱼ into Aᵢ → Aⱼγ; then remove the immediate left recursion of Aᵢ. Example S → AA | 0; A → SS | 1: S has none. Substitute S in A: A → AAS | 0S | 1; remove: A → 0SA′ | 1A′; A′ → ASA′ | ε. Final: S → AA | 0; A → 0SA′ | 1A′; A′ → ASA′ | ε.

Order of work: ambiguity → left recursion → left factoring, then compute FIRST/FOLLOW and check the LL(1) conditions. Left recursion elimination can create a common prefix, so check for factoring afterwards.
Read: Dragon Book §4.3 “Writing a Grammar” (§4.3.2 eliminating ambiguity, §4.3.3 elimination of left recursion, §4.3.4 left factoring).

3. FIRST and FOLLOW slides 416–422

  • FIRST(X): the terminals that can begin a string derived from X. If X is a terminal, FIRST(X) = {X}. If X → ε then ε ∈ FIRST(X). For X → Y₁Y₂…Yₖ: add FIRST(Y₁)−{ε}; if ε ∈ FIRST(Y₁) also add FIRST(Y₂)−{ε}, and so on; add ε if all Yᵢ derive ε. FIRST of a string uses the same rule.
  • FOLLOW(A): the terminals that can appear immediately to the right of A in some sentential form. (1) Put $ in FOLLOW(start). (2) For B → αAβ: add FIRST(β)−{ε} to FOLLOW(A). (3) For B → αA, or B → αAβ with ε ∈ FIRST(β): add FOLLOW(B) to FOLLOW(A). Repeat until nothing changes. FOLLOW never contains ε.

Tip: compute FIRST for all non-terminals first (bottom-up through the productions), then FOLLOW.

4. LL(1) conditions, the table and the parse

  • LL(1) grammar: for every pair of alternatives A → α | β: (1) FIRST(α) ∩ FIRST(β) = ∅; (2) at most one of α, β derives ε; (3) if β ⇒* ε then FIRST(α) ∩ FOLLOW(A) = ∅. Equivalent practical test: the table has no cell with two productions. Never LL(1): left-recursive, ambiguous or non-left-factored grammars.
  • Table M[A, a]: for each production A → α: (1) for every terminal a ∈ FIRST(α), put A → α in M[A, a]; (2) if ε ∈ FIRST(α), put A → α in M[A, b] for every b ∈ FOLLOW(A) (including $). Empty cells are errors.
  • Parsing algorithm: stack starts S $ (top on the left), input ends with $. Let X be the top and a the next input.
    • X = a = $: accept. X = terminal = a: pop and advance. X terminal ≠ a: error.
    • X non-terminal: look at M[X, a]; if it holds X → Y₁…Yₖ, pop X and push Yₖ…Y₁ (so Y₁ is on top; for ε push nothing). Empty cell: error.
  • Impact: each step is one table lookup, so parsing is linear time with no backtracking; the stack holds the predicted rest of the derivation (a leftmost derivation, written in the “Output” column).

8. Theory questions asked

“Describe the syntax analyzer (parsing) phase…” Spring 2025, Fall 2024 · 4 marks

Role (section 1), the input/output (tokens in, parse tree out), what it checks (structure, not meaning), and the algorithms with pros and cons: recursive descent (+ simple, hand-written; − backtracking, left recursion), predictive LL(1) (+ linear, no backtracking, table-driven; − restricted grammar class, needs rewriting), SLR/LALR (+ larger class, tools; − tables big, hard by hand), canonical LR(1) (+ strongest; − very large tables).

“Key properties of an LL(1) grammar and their impact” Spring 2024

The conditions of section 4. Impact: (1) no backtracking, one table lookup per step; (2) no left recursion, or the parser would loop; (3) left-factored, or it could not choose; (4) unambiguous, so each string has exactly one parse. Any violation puts two productions in one cell.

“Algorithm for the predictive parsing table; conditions; challenges” Fall 2023

Algorithm in section 4. Challenges if not LL(1): multiple entries in a cell, which come from left recursion, common prefixes or ambiguity; fix by rewriting the grammar, by choosing one production by a rule (dangling else), or by moving to LR parsing.

9. Mistakes & practice

  • Leaving ε out of FIRST(A′) or using FIRST instead of FOLLOW for the ε-rule in the table.
  • Putting ε in a FOLLOW set; FOLLOW holds only terminals and $.
  • Pushing the production body in the wrong order. The first symbol must end on top.
  • Forgetting that FOLLOW(A′) = FOLLOW(A) when A → βA′.
  • Calling a grammar LL(1) because it has no left recursion: check common prefixes and FIRST/FOLLOW overlaps.

P1. Is S → aSb | ε LL(1)?

AnswerFIRST(aSb)={a}; ε ∈ FIRST(ε); FOLLOW(S)={b,$}. {a} ∩ {b,$} = ∅ ⇒ LL(1). M[S,a]=aSb; M[S,b]=M[S,$]=ε.

P2. Compute FIRST and FOLLOW for S → ABC; A → a | ε; B → b | ε; C → c.

AnswerFIRST(A)={a,ε}, FIRST(B)={b,ε}, FIRST(C)={c}, FIRST(S)={a,b,c}. FOLLOW(S)={$}; FOLLOW(A)={b,c}; FOLLOW(B)={c}; FOLLOW(C)={$}.

P3. Why is S → Sa | b not LL(1), and what is its LL(1) form?

AnswerLeft recursion: FIRST(Sa) = FIRST(b) = {b}, so M[S,b] has two entries. Fix: S → bS′; S′ → aS′ | ε.

P4. Trace b$ with the table of Spring 2024 (S → AcBd) and say where the error is found.

AnswerS → A c B d; A → b A; match b; now input is $ and the top is A: M[A,$] is empty, so error. (Panic mode would pop A using FOLLOW(A) = {c} as the sync set, then report the missing c.)
