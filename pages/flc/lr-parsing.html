LR Parsing (LR(0), SLR(1), LR(1), LALR)

LR parsing is in every paper (Q2a, 7 marks, plus Q1 and Q3 variants), but your slides only introduce bottom-up/shift-reduce parsing, so this page follows the Dragon Book (Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools, 2nd ed.) and marks the material [book]. 1. Bottom-up parsing and shift-reduce [book] Dragon Book §4.5

  • Bottom-up parsing builds the parse tree from the leaves up to the start symbol. It is a reverse rightmost derivation: it repeatedly reduces a substring matching the body of a production to its head.
  • Example id + id with E→E+T|T, T→T*F|F, F→(E)|id. Rightmost derivation: E ⇒ E+T ⇒ E+F ⇒ E+id ⇒ T+id ⇒ F+id ⇒ id+id. The parser performs these steps backwards.
  • Handle: the substring that matches a production body and whose reduction is one step of a rightmost derivation in reverse. The parser must find the handle, not just any matching body.
  • Shift-reduce parser: a stack (grammar symbols) and the input. Four actions: shift (push the next token), reduce (pop the body, push the head), accept, error.
  • Compare with top-down: top-down (LL) predicts productions from the start symbol and needs the grammar free of left recursion and left factoring; bottom-up (LR) handles left recursion and a larger class of grammars and is what real tools use (Yacc/Bison generate LALR(1) parsers).

LR(k)

Left-to-right scan, Rightmost derivation in reverse, k lookahead symbols (usually 0 or 1). The LR parser keeps a stack of states (each state summarizes the grammar symbols below it) and uses two tables:

  • ACTION[state, terminal] = sn (shift and go to state n), rk (reduce by production k), acc (accept) or blank (error).
  • GOTO[state, non-terminal] = next state after a reduction.

The driver algorithm

  1. Let s be the state on top of the stack and a the next input symbol; look up ACTION[s, a].
  2. Shift n: push a and state n; advance the input.
  3. Reduce A → β: pop 2·|β| entries (the |β| symbols and their states), let t be the new top state, push A and GOTO[t, A]. (Do not consume input.)
  4. Accept: stop with success. Blank: syntax error.

2. Items, closure, goto: building the LR(0) automaton [book] §4.6.2

  • Augment the grammar: add S′ → S (new start). Acceptance is reducing by S′→S, i.e. reaching S′ → S• on $.
  • LR(0) item: a production with a dot marking how much of the body has been seen: A → α•β. A → •XYZ = nothing seen; A → XYZ• = complete (reduce). A production A → ε gives the single item A → •.
  • Closure(I): add every item of I; then, whenever an item A → α•Bβ is in the set (dot before a non-terminal B), add B → •γ for every production of B; repeat until nothing new.
  • Goto(I, X): move the dot over X in every item A → α•Xβ of I, giving A → αX•β, then take the closure. The result is a new state (or an existing one).
  • Canonical collection: I₀ = closure({S′ → •S}); keep applying goto for every symbol X until no new sets appear. Sets are the states; goto is the transition function, so the whole thing is a DFA that recognizes viable prefixes.
Exam layout: (1) numbered productions incl. S′; (2) list states I₀, I₁… with all items (kernel + closure items); (3) draw or list the transitions; (4) fill the table; (5) state conflicts. Write a state’s closure items right under its kernel items to show you applied closure.

  • Shift/reduce (S/R) conflict: one cell has both “shift” and “reduce”. Typical cause: a state with a complete item A → α• and another item with the dot before a terminal (B → γ•aδ), e.g. E → T• and T → T•*F. Ambiguity also causes it (dangling else: S → if E then S• vs S → if E then S• else S; E → E+E• vs E → E•+E).
  • Reduce/reduce (R/R) conflict: a state has two complete items (A → d• and B → d•) and their lookaheads overlap.
  • A grammar is LR(0) if no state has a conflict with reduction in all columns; SLR(1) if the FOLLOW-restricted table has no multiple entries. Conflicts that remain mean the grammar is not in that class; use a bigger class (LALR/LR(1)), rewrite the grammar, or give precedence rules (Yacc).

8. LR(1) and LALR(1) in short [book] §4.7

  • LR(1) item: [A → α•β, a], a = lookahead terminal expected after the production is complete. Closure: for [A→α•Bβ, a] add [B→•γ, b] for every b ∈ FIRST(βa). Reduce A→α• only on its own lookahead a (stronger than FOLLOW).
  • LALR(1): merge LR(1) states with the same core (same LR(0) items), union the lookaheads. Same number of states as SLR/LR(0), almost as powerful as LR(1); merging can introduce reduce/reduce conflicts (never shift/reduce), as in section 6. Yacc/Bison generate LALR(1).
  • Error handling: blank ACTION cell = error; panic mode pops states until one with a transition on a special error token (Yacc), then discards input until a synchronizing token; phrase-level recovery and error productions are also used.
Read: Dragon Book §4.7 “More Powerful LR Parsers” (§4.7.1 canonical LR(1) items, §4.7.4 canonical LR(1) tables, §4.7.5 LALR tables); §4.9 “Parser Generators” (Yacc).

9. Theory questions asked

Shift/reduce conflicts: what, why, example Spring 2024, Spring 2023, Fall 2024

See section 3. Give: definition (parser cannot decide between shift and reduce), cause (ambiguous grammar, or insufficient lookahead), and one example. Example answer: grammar E → E+E | E*E | id is ambiguous. In the state with items E → E+E• and E → E•*E, on input * the parser may reduce (making + bind first) or shift (making * bind first). Resolve with precedence/associativity rules or by rewriting the grammar to the E, T, F form. Reduce/reduce conflicts come from two complete items in one state (section 6).

Steps to build an SLR parsing table Spring 2024, 4 marks

1. Augment (S′→S). 2. Build the canonical LR(0) collection with closure and goto. 3. Compute FOLLOW for every non-terminal. 4. For each state: shift on terminals after the dot; reduce A→α on FOLLOW(A) for complete items; accept for S′→S• on $; fill GOTO for non-terminals. 5. Leave blanks as errors; any cell with two entries means the grammar is not SLR(1).

Top-down vs bottom-up, which is more common? Fall 2023, 4 marks

Top-down builds the tree from the root, leftmost derivation, predicts productions, needs left recursion removed (recursive descent, LL(1)). Bottom-up builds from the leaves, reverse rightmost derivation, shift-reduce, accepts left-recursive and a bigger class of grammars (LR). Bottom-up (LR/LALR) is the common choice in generated compilers (Yacc/Bison) because it handles more grammars and detects errors early; hand-written compilers often use recursive descent for clearer error messages and easier code.

10. Mistakes & practice

  • Forgetting the augmented production, or the closure items inside a state.
  • Pushing only states when shifting/reducing and losing the symbols (write symbols and states, or only states, but be consistent).
  • Popping the wrong number of entries on a reduce: it is |body| symbols (2·|body| stack entries if you write symbols and states).
  • Filling reduce entries across all columns for an SLR question (use FOLLOW).
  • Calling a grammar “LR(0)” because there are no conflicts in the SLR table; check the LR(0) table.

P1. Is S → aS | b LR(0)? Build the item sets.

AnswerI0: S′→•S, S→•aS, S→•b. I1 S: S′→S•. I2 a: S→a•S, S→•aS, S→•b. I3 b: S→b•. I4 (I2,S): S→aS•. States I3 and I4 have only one complete item and no other items, so there are no conflicts: LR(0).

P2. Which grammar class can parse E → E+E | id without rewriting?

AnswerNone of the plain classes: the grammar is ambiguous, so a state has E→E+E• and E→E•+E (S/R conflict even in LR(1)). Yacc resolves it by declaring + left-associative, which picks reduce.

P3. A parser stack is 0 E 1 + 6 T 9 with next token $ in the table of section 5. What happens?

AnswerACTION[9,$] = r1 (E→E+T): pop three symbols (and their states), top state 0, GOTO[0,E] = 1, stack 0 E 1; then accept on $.

P4. Order by power: LALR(1), LR(0), LR(1), SLR(1).

AnswerLR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ LR(1).
