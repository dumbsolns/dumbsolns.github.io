What · Why · How

Every topic in the course on one page, three questions each: what it is, why it exists, how it does its job. Use it for a first pass before the exam; follow the links for methods, worked examples and past-paper questions.

1. Language processing system & compiler structure

Slides 3–22

WhatThe chain that turns source code into a running program: preprocessor (macros, includes) → compiler → assembler (object code) → linker (merges modules, resolves references) → loader (puts the program in memory). A compiler translates the whole program; an interpreter translates and runs one statement at a time.
WhyMachines run only machine code, people write high-level code. Splitting the job into stages keeps each simple, supports separate compilation (hence relocatable object code), and a front end / back end split gives portability: one front end per language, one back end per machine.
HowThe compiler has an analysis half (lexical, syntax, semantic analysis → intermediate code and symbol table) and a synthesis half (optimization, code generation). The symbol table and error handler are used by every phase.

2. Lexical analysis

Slides 25–31, 285–291

WhatThe first phase: reads the character stream and groups it into tokens. Token = category (id, keyword, operator), lexeme = the matched text, pattern = the rule (a regular expression) describing the lexemes.
WhyThe parser then works on a short stream of tokens instead of raw characters. The lexer also removes whitespace and comments, expands macros, links errors to line numbers and creates symbol-table entries.
HowEach token pattern is a regular expression, compiled to an NFA then a DFA. The lexer takes the longest match (earlier rule wins ties), looks keywords up in a reserved table, and returns <token, attribute> such as <id, 3> (index into the symbol table). A lexical error is text matching no pattern; recovery deletes, inserts, replaces or transposes one character.

3. Regular expressions

Slides 32–38

WhatA notation for regular languages: the symbols, ε and ∅, combined with union (+ or |), concatenation and star. Precedence: star > concatenation > union.
WhyIt is a compact way to specify token patterns and simple string sets, and it is exactly as powerful as a finite automaton, so any regular expression can be turned into a machine automatically.
HowTo write one, split the language into alternatives, a sequence and repeated parts (“anything, special part, anything” is (0+1)*part(0+1)*). To run one, build an ε-NFA by structure (the Thompson construction) and convert it. Algebraic laws ((R*)* = R*, (R+S)* = (R*S*)*) simplify or compare expressions.

Deep dive: regular expressions · DFA design & RE → DFA

4. Finite automata: DFA, NFA, ε-NFA

Slides 39–284

WhatA finite-state machine (Q, Σ, δ, q₀, F). DFA: exactly one move per state and symbol. NFA: δ returns a set of states, accepts if some path ends in F. ε-NFA: also moves without reading input. All three accept exactly the regular languages.
WhyIt recognizes a language using no memory beyond the current state, so it is fast: a DFA does one table lookup per character, which is why lexers are DFAs. NFAs and ε-NFAs are easier to design and to build from regular expressions.
HowThe extended function δ̂ applies δ along the whole string (a set of states for NFAs). To design a DFA, decide what each state must remember (pattern progress, a parity, a count mod n), mark finals, add a dead state for impossible continuations, and make sure every state has an arrow for every symbol.

Deep dive: DFA design · definitions and δ̂

5. Automata conversions & minimization

Slides 184–284

WhatThree procedures: ε-NFA → NFA (remove ε-moves with the ε-closure), NFA → DFA (subset construction), and DFA minimization (merge equivalent states).
WhyComputers execute deterministic machines, so designs made as NFAs must be converted. The conversions prove all models are equally powerful, and minimization gives the smallest machine, which means smaller lexer tables.
Howε-removal: δ′(q,a) = ECLOSE(δ(ECLOSE(q), a)). Subset construction: start at the closure of q₀, build only reachable subsets, a subset is final if it contains an NFA final state. Minimization (table filling): mark final/non-final pairs, mark a pair if some symbol leads to a marked pair, merge the unmarked pairs.

Deep dive: automata conversions

6. Context-free grammars & ambiguity

Slides 292–341

WhatA grammar G = (V, T, P, S) whose productions have a single variable on the left (A → α), so it is “context-free”. It generates a context-free language through derivations (leftmost or rightmost) and parse trees. A grammar is ambiguous if a string has two parse trees.
WhyRegular expressions cannot express nesting (balanced brackets, if-else, nested expressions), which is the core of programming-language syntax. The grammar both defines the language and is what a parser is built from. Ambiguity must go because the parse tree fixes the meaning.
HowDesign by finding the nested or repeated structure and giving each part a variable (S → 0S1 | 01). Remove ambiguity by adding precedence levels (E→E+T|T, T→T*F|F, F→(E)|id) or by disambiguating rules (nearest then for else).

Deep dive: CFG, simplification & CNF

7. CFG simplification & Chomsky Normal Form

Slides 306–341

WhatSimplification removes useless symbols (non-generating, non-reachable), ε-productions and unit productions. CNF restricts every production to A → BC or A → a (plus S → ε).
WhyCleaner grammars are smaller and easier to analyze. A normal form gives algorithms and proofs one predictable shape: CNF parse trees are binary, so a string of length n takes exactly 2n − 1 derivation steps, and parsing algorithms such as CYK need CNF.
HowOrder: nullable set → remove ε → remove unit rules → remove non-generating then non-reachable symbols. CNF then isolates terminals in long bodies with new variables (Xₐ → a) and splits bodies longer than two into chains of binary productions.

Deep dive: simplification · CNF

8. Pushdown automata

Slides 342–361

WhatA finite automaton plus a stack: P = (Q, Σ, Γ, δ, q₀, Z, F). It accepts by final state or by empty stack. Deterministic PDAs are strictly weaker than nondeterministic ones.
WhyThe stack gives the memory needed for counting and matching (aⁿbⁿ, balanced brackets, palindromes), so a PDA recognizes exactly the context-free languages. It is also the machine model behind parsers.
HowEach move looks at the state, the next input (or ε) and the stack top, then pops the top and pushes a string. Typical design: push while reading the first part, switch state at the boundary (guessing it with an ε-move if it is not marked, as in wwᴿ), pop-match the second part, accept when only the bottom marker is left. A CFG becomes a PDA by expanding variables on the stack and matching terminals.

Deep dive: pushdown automata

9. Syntax analysis (parsing)

Slides 364–380

WhatThe second compiler phase: it checks that the token stream is generated by the grammar and builds the parse tree (or AST). It checks structure only, not meaning.
WhyLater phases need a tree, not a flat token list, and programs with broken structure (missing brackets, wrong statement shape) must be rejected with a useful message.
HowTwo families: top-down (start symbol down, leftmost derivation: recursive descent, LL(1)) and bottom-up (tokens up, reverse rightmost derivation: LR, SLR, LALR). One token of lookahead usually decides the next step.

Deep dive: parser role & comparison

10. Top-down parsing & LL(1)

Slides 380–422

WhatA predictive parser: Left-to-right scan, Leftmost derivation, 1 lookahead symbol, driven by a stack and a table M[A, a].
WhyIt never backtracks, so it runs in linear time, and it is simple to build by hand or from a table. Its price: the grammar must be rewritten first.
How(1) Remove ambiguity, left recursion (A → Aα | β becomes A → βA′, A′ → αA′ | ε) and left factoring. (2) Compute FIRST and FOLLOW. (3) For A → α, put it in M[A, a] for a ∈ FIRST(α), and for a ∈ FOLLOW(A) when α can derive ε; two entries in a cell means “not LL(1)”. (4) Parse: pop a non-terminal and push its body reversed, match terminals, accept at $.

Deep dive: top-down & LL(1) parsing

11. Bottom-up parsing & LR

Introduced in the slides; full treatment in the textbook

WhatShift-reduce parsing: a stack of states plus ACTION/GOTO tables. Classes LR(0), SLR(1), LALR(1), LR(1) differ in how much lookahead they use for reductions.
WhyIt accepts left-recursive grammars and a much larger class of grammars than LL(1), detects errors early, and is what parser generators (Yacc, Bison) produce.
HowAugment the grammar, build the LR(0) item automaton with closure and goto, fill the table (SLR reduces only on FOLLOW(A)). Run: shift pushes a token, reduce pops the body and takes GOTO on the head, accept on S′ → S• with $. Conflicts: shift/reduce (ambiguity, weak lookahead) and reduce/reduce.

Deep dive: LR parsing

12. Syntax error handling & recovery

Slides 423–428

WhatStrategies that let the parser continue after finding an error: panic mode, phrase-level correction, error productions, global correction.
WhyStopping at the first error forces one fix per compile. A good compiler reports as many real errors as possible, accurately and with line numbers, without a flood of false follow-on messages.
HowPanic mode discards tokens up to a synchronizing token (;, }; in LL(1) the FOLLOW set). Phrase-level repairs locally (insert a missing ;). Error productions put common mistakes into the grammar. Global correction searches for the closest valid program but is too costly in practice.

Deep dive: error recovery table

13. Semantic analysis & syntax-directed translation

Slides 431–451

WhatSemantic analysis checks meaning: types, scope, declarations, parameter matching. SDT attaches attributes and rules to the grammar (a syntax-directed definition = CFG + semantic rules). Synthesized attributes come from children, inherited ones from parent or siblings.
WhyA parse tree says a program is well formed, not what it means. Rules over the tree compute values, check types and generate code. Many errors (undeclared variable, type mismatch) are invisible to a CFG.
HowAnnotate the parse tree: S-attributed definitions use only synthesized attributes (bottom-up, actions at the end); L-attributed ones may inherit only from the parent and left siblings (top-down, left to right). Symbol-table lookups supply declarations. Examples: desk calculator values, infix to postfix, code generation.

Deep dive: SDT & three-address code

14. Intermediate code & three-address code

Textbook topic used by the exam SDD

WhatA linear, machine-independent code with at most three addresses per instruction (x = y op z), compiler-made temporaries, labels and jumps. Stored as quadruples, triples or indirect triples.
WhyIt is a bridge between front end and back end: N languages and M machines need N + M tools, not N × M. It is simple enough to optimize and easy to translate to any target.
HowAn SDD with newtemp and gen builds E.place and E.code bottom-up: a := b*-c + b*-c becomes t1 := uminus c; t2 := b*t1; t3 := uminus c; t4 := b*t3; t5 := t2+t4; a := t5. Control flow becomes labels and conditional jumps.

Deep dive: three-address code · control flow

15. Code optimization

Slides 454–484

WhatTransformations that make code faster or smaller while keeping its meaning. Local (within a basic block), peephole (a small window of target code) and global.
WhyNaive translation wastes time and memory: repeated computations, dead code, needless jumps. Optimizing reduces CPU and memory use at no cost to the programmer.
HowSplit the code into basic blocks (leaders: first instruction, jump targets, instructions after jumps) and a flow graph. Apply peephole rules (redundant loads, constant folding, unreachable code, flow-of-control, algebraic simplification, strength reduction, machine idioms), common sub-expression elimination and dead-code elimination.

Overview: summary, section 9

16. Code generation

Slides 487–499

WhatThe last phase: turns optimized intermediate code plus symbol-table data into target code (absolute machine code, relocatable machine code, or assembly).
WhyIt produces the program the machine actually runs, and its choices (instruction selection, register allocation, evaluation order) decide the speed and size of the result.
HowUsing a target model (registers, two-address instructions, addressing modes), pick instructions for each IR statement, keep values in registers to avoid loads and stores, and reorder independent computations. Compare options by cost: instruction cost = 1 + operand costs (register 0, memory or constant 1); MOV b,R0; ADD c,R0; MOV R0,a costs 6, but with addresses in registers two instructions cost 2.

Overview: summary, section 10
