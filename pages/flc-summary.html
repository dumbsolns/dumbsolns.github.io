1. Introduction & Compiler Architecture

Slides 3–22

  • Compiler translates the whole source program into target code (object code); an interpreter translates and executes one statement at a time.
  • Language processing system: preprocessor (macros, file inclusion) → compiler → assembly → assembler (object file) → linker (merges object files, resolves references) → loader (puts executable in memory).
  • Cross-compiler: runs on platform A, generates code for B. Source-to-source: one high-level language to another.
  • Analysis (front end): lexical, syntax, semantic analysis → intermediate representation + symbol table. Synthesis (back end): code optimization and code generation → target code.
  • Phases and tools: Lexical (RE → NFA → DFA, tool FLEX) · Syntax (CFG/BNF, LL/LR/SLR/LALR, tool Bison) · Semantic (syntax-directed translation) · Intermediate code (3-address code) · Optimizer (loop optimization, register allocation, peephole) · Code generator.
  • Symbol table and error handler interact with every phase. Errors by phase: lexical (invalid token), syntax (missing ;, unmatched parentheses), semantic (undeclared variable, type mismatch), intermediate (division by constant zero).
Read: Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools (Dragon Book, 2nd ed.), Ch. 1 “Introduction” (Language Processors; The Structure of a Compiler).

2. Lexical Analysis & Symbol Tables

Slides 25–31, 285–291

  • The lexer converts a character stream to a token stream, strips whitespace/comments, expands macros, and relates errors to line numbers. The parser calls “get next token” on demand.
  • Token = abstract unit (id, keyword, operator, constant, punctuation). Lexeme = the actual character sequence matched. Pattern = the rule describing a token's lexemes (usually a regular expression).
  • Token format: <token name, attribute value>, e.g. <id, 1> where the attribute points to a symbol-table entry. Operators/keywords usually carry no attribute.
  • Lexical error: a character sequence matching no pattern (illegal character, misspelling).
  • Symbol table: stores name, type, scope, etc. for each identifier; built during analysis, used by all phases. Implementations: list, binary search tree, hash table (most common). Operations: insert, lookup(symbol) (returns 0 if absent), plus scope handling.
  • Static (lexical) scoping: search current block, then enclosing blocks, then global. Dynamic scoping: search current block then calling functions.
Read: Dragon Book Ch. 3 “Lexical Analysis” (The Role of the Lexical Analyzer; Specification of Tokens; Recognition of Tokens); Ch. 2 “A Simple Syntax-Directed Translator” (Symbol Tables). Also Louden, Compiler Construction: Principles and Practice, Ch. 2 “Scanning”.

3. Formal Language Basics & Regular Expressions

Slides 32–38

  • Alphabet Σ: finite non-empty set of symbols. String: finite sequence of symbols; |w| = length; |ε| = 0.
  • Prefix/suffix (proper = not the whole string). Concatenation xy. Σ* = all strings including ε (Kleene star); Σ⁺ = all non-empty strings.
  • Language: any subset L ⊆ Σ*. Natural languages evolve; formal grammars are defined (stipulated).
  • Regular expression rules: ∅ → {} · ε → {ε} · a → {a} · E+F (or E|F) → union · EF → concatenation · E* → closure. Precedence: star > concatenation > union.
  • Regular languages are closed under union and concatenation (and star). A language is regular iff some finite automaton accepts it.
  • Useful identities: Rε = R, R+∅ = R, L(1∅) = ∅. Examples: all strings = (0+1)*; start with 11 = 11(0+1)*; end with 00 = (0+1)*00; even length = ((0+1)(0+1))*; exactly one 1 = 0*10*.
Read: Hopcroft, Motwani, Ullman (HMU), Introduction to Automata Theory, Languages, and Computation (3rd ed.), Ch. 1 “Automata: The Methods and the Madness” (alphabets, strings, languages) and Ch. 3 “Regular Expressions and Languages”. Sipser, Introduction to the Theory of Computation, Ch. 1 “Regular Languages” (§1.3 Regular Expressions).

4. Finite Automata: DFA, NFA, ε-NFA, Minimization

Slides 39–284

DFA

  • 5-tuple (Q, Σ, δ, q₀, F): states, alphabet, transition function δ: Q×Σ→Q, start state, final states. Exactly one move per state/symbol.
  • Extended δ̂: basis δ̂(q, ε) = q; induction for w = xa: δ̂(q, xa) = δ(δ̂(q, x), a).
  • Language: L(A) = { w | δ̂(q₀, w) ∈ F }.
  • Design tips: decide what each state “remembers” (last symbols seen, count mod n, parity); add a dead/trap state for rejected prefixes; strings ending in a pattern need states tracking pattern progress.

NFA

  • δ returns a set of states (zero or more): δ: Q×Σ → 2^Q. It can be “in several states at once.”
  • L(A) = { w | δ̂(q₀, w) ∩ F ≠ ∅ }: accepted if at least one path ends in a final state.
  • NFAs are often easier to design (e.g. strings ending in 01, or ending in ab/bc/ca) but accept exactly the same languages as DFAs.

NFA → DFA (subset construction)

  • Same alphabet; start state = {q₀}; Q_D = subsets of Q_N; δ_D(S, a) = ∪ δ_N(p, a) over p ∈ S; a DFA state is final if it contains an NFA final state.
  • Worst case 2ⁿ states, but build only the subsets reachable from the start (lazy construction).

ε-NFA

  • Allows ε-moves. ECLOSE(q) = all states reachable from q using only ε-moves (includes q).
  • Eliminate ε: δ'(q, a) = ECLOSE( δ( ECLOSE(q), a ) ); q is final if ECLOSE(q) contains a final state. Then apply subset construction if a DFA is needed.

DFA minimization (table-filling)

  • Equivalent states p ≡ q iff for every string z, δ̂(p,z) ∈ F ⇔ δ̂(q,z) ∈ F.
  • Algorithm: (1) make a table of all unordered state pairs; (2) mark every pair of one final + one non-final state; (3) for each unmarked pair (p,q) and symbol a, look at (δ(p,a), δ(q,a)): if that pair is marked, mark (p,q) and recursively mark pairs that depend on it; otherwise record (p,q) as a dependency of that pair; (4) merge unmarked pairs into one state.
  • Also remove unreachable states first.
Exam tip: expect to convert an NFA/ε-NFA to a DFA and then minimize. Show the transition table, mark final states with *, and list the subsets explicitly.
Read: HMU Ch. 2 “Finite Automata” (DFA, NFA, “Finite Automata with Epsilon-Transitions”, equivalence of DFA and NFA) and Ch. 4 “Properties of Regular Languages” (§4.4 Equivalence and Minimization of Automata). Sipser Ch. 1 “Regular Languages” (§1.1 Finite Automata, §1.2 Nondeterminism). Dragon Book §3.7 “From Regular Expressions to Automata”.

5. Context-Free Grammars & Normal Forms

Slides 292–341

  • CFG G = (V, T, P, S): variables, terminals (V∩T = ∅), productions A → α with α ∈ (V∪T)*, start symbol. “Context-free” because replacing A does not depend on surrounding symbols. Used by parsers (yacc, bison) and to describe XML.
  • Examples: S → 01 | 0S1 generates {0ⁿ1ⁿ | n>0}; palindromes P → ε | 0 | 1 | 0P0 | 1P1.
  • Derivations: leftmost (always expand leftmost variable), rightmost, or a parse tree (interior nodes = variables, leaves = terminals).
  • Ambiguity: a string with more than one parse tree (e.g. E → E+E | E*E | (E) | x | y | z on x+y+z).

Simplification (do in this order)

  • Useless variables: remove non-generating variables (cannot derive any terminal string) first, then non-reachable ones (cannot be reached from S).
  • ε-productions: find nullable variables (A ⇒* ε); for each production add every version with nullable symbols omitted (A → X₁X₂X₃X₄ with X₁, X₃ nullable gives 4 versions); drop A → ε (keep S → ε if S nullable).
  • Unit productions A → B: collapse cycles; for each path A ⇒ … ⇒ α (non-unit) add A → α directly, then delete unit rules.

Chomsky Normal Form (CNF)

  • Every production is A → BC or A → a (plus S → ε allowed). Every CFG can be converted.
  • Steps: (1) remove ε, unit and useless productions; (2) replace terminals inside mixed/long bodies with new variables (A → bCD becomes A → BCD, B → b); (3) break bodies longer than 2 into chains of binary productions.
Read: HMU Ch. 5 “Context-Free Grammars and Languages” (§5.1 CFG, §5.2 Parse Trees, §5.4 Ambiguity) and Ch. 7 “Properties of Context-Free Languages” (§7.1 Normal Forms: eliminating useless symbols, ε- and unit productions, CNF). Sipser Ch. 2 “Context-Free Languages” (§2.1 CFG, Chomsky normal form). Dragon Book §2.2 “Syntax Definition”, §4.2 “Context-Free Grammars”.
Go deeper: CFG, simplification & CNF (incl. CFG-design questions)

6. Pushdown Automata (PDA)

Slides 342–361

  • PDA = finite automaton + stack (LIFO). Recognizes exactly the context-free languages.
  • 7-tuple (Q, Σ, Γ, δ, q₀, Z, F): states, input alphabet, stack alphabet, transition function, start state, initial stack symbol, final states. Each move reads the stack top (and optionally an input symbol or ε), then pushes/pops.
  • Turnstile ⊢ = one move, ⊢* = zero or more moves. Instantaneous description (state, remaining input, stack).
  • Acceptance: by final state or by empty stack.
  • Worked examples: aⁿbⁿ (push a, pop a per b) · aⁿb²ⁿ (push two symbols per a) · wwᴿ (push, guess the middle nondeterministically, pop) · equal / unequal numbers of a's and b's (empty-stack acceptance).

7. Syntax Analysis (Parsing)

Slides 364–428

  • Role of the parser: check that the token string is generated by the grammar, build the parse tree/AST, detect syntax errors and recover. It cannot catch re-declaration, use before initialization, or type mismatch (semantic phase).
  • Why CFG not RE: every regular language is context-free, not vice versa. REs suit lexical structure (identifiers, constants); CFGs handle nesting (balanced parentheses, if-else).
  • Terminals vs tokens: token names are the terminals of the grammar; attribute values live in the symbol table.
  • Parser types: top-down (LL, leftmost derivation) vs bottom-up (shift-reduce; LR, SLR, LALR).

Grammar transformations for top-down parsing

  • Ambiguity removal: (1) disambiguating rules (precedence, left associativity) without changing the grammar, or (2) rewrite the grammar so higher-precedence operators bind deeper (E → E+T | T; T → T*F | F; F → (E) | id).
  • Left factoring: A → αβ₁ | αβ₂ | γ becomes A → αA' | γ; A' → β₁ | β₂.
  • Immediate left recursion: A → Aα | β becomes A → βA'; A' → αA' | ε. General: A → Aα₁|…|Aαₘ|β₁|…|βₙ becomes A → β₁A'|…|βₙA'; A' → α₁A'|…|αₘA'|ε.
  • Indirect left recursion: order the variables, substitute earlier variables into later productions, then remove the resulting immediate recursion (example S → AA | 0, A → SS | 1).
  • Standard result: E → TE'; E' → +TE' | ε; T → FT'; T' → *FT' | ε; F → (E) | id.

Predictive (LL(1)) parsing

  • LL(1): Left-to-right scan, Leftmost derivation, 1 lookahead symbol. No backtracking; uses a stack + parsing table; stack and input both end with $. Grammar must have no left recursion and no left factoring (and be unambiguous).
  • FIRST(X): terminals that can begin strings derived from X (include ε if X ⇒* ε). If X is a terminal, FIRST = {X}.
  • FOLLOW(A): terminals that can appear right after A. FOLLOW(start) contains $; for B → αAβ add FIRST(β)−{ε}; if β ⇒* ε (or is empty) add FOLLOW(B). FOLLOW never contains ε.
  • Table construction: for each A → α: put the production in M[A, a] for every a ∈ FIRST(α); if ε ∈ FIRST(α), put it in M[A, b] for every b ∈ FOLLOW(A). Any cell with two entries means the grammar is not LL(1).

  • Parse run (id+id*id): stack starts E$. Top is a non-terminal: look up M[top, input] and replace it by the production body reversed. Top is a terminal: match and advance. Accept when both stack and input are down to $.

Error recovery strategies

  • Panic mode: skip input until a synchronizing token (;, }); simple, may skip a lot.
  • Phrase-level: local correction (e.g. insert a missing ;).
  • Error productions: add productions for common mistakes; hard to maintain.
  • Global correction: find the closest error-free program with the fewest insertions/deletions/changes; too costly in practice.
Exam tip: a typical question gives a grammar, asks you to remove left recursion/factoring, compute FIRST/FOLLOW, fill the LL(1) table, and trace a string with a stack/input/action table.

8. Semantic Analysis & Syntax-Directed Translation

Slides 431–451

  • A plain parse tree has no meaning attached. CFG + semantic rules = Syntax-Directed Definition (SDD). Semantic analysis does scope resolution, type checking, array-bound checking.
  • Semantic errors: type mismatch, undeclared variable, reserved-identifier misuse, multiple declaration in one scope, out-of-scope access, actual/formal parameter mismatch.
  • Two methods: attribute grammars (SDD) and syntax-directed translation schemes (rules/actions embedded in the production). Example: E → E + T { E.value = E.value + T.value }.
  • Synthesized attribute: value computed from children (S → ABC: S gets values from A, B, C).
  • Inherited attribute: value taken from parent and/or siblings.

  • L-attributed check for A → X Y: X may use A's inherited attributes only; Y may use A and X. Anything depending on a right sibling (e.g. X.i = A.i + Y.i) violates the rule.
  • Worked examples: desk-calculator evaluation with val; converting infix to postfix with concatenation ||: E → E+T { E.val = E.val || T.val || '+' }. The annotated parse tree for 3+2-4 yields postfix 3 2 + 4 -.

9. Code Optimization

Slides 454–484

  • Goal: use fewer resources (CPU, memory) and run faster without changing program meaning. Methods: remove unneeded code, reorder statements.
  • Basic blocks: straight-line code with one entry and one exit. Find leaders: the first instruction; any jump target; any instruction right after a jump. A block runs from a leader up to (not including) the next leader. Blocks plus jump edges form the flow graph (the quick-sort 3-address code splits into B1–B6).

  • Common sub-expression elimination (CSE): if an expression (e.g. 4 * i) was already computed in the block and its operands are unchanged, reuse the earlier temporary. Applied step by step to the quick-sort blocks B5/B6, which also shows copy propagation.
  • Dead-code elimination: remove statements whose results are never used; typically cleans up after CSE and copy propagation.

10. Code Generation

Slides 487–499

  • Final phase: takes the (optimized) IR plus symbol-table information and produces the target program. Input is assumed error-free (type-checked). IR forms: postfix, three-address code, stack-machine code, syntax tree, DAG.
  • Design issues: input to the generator, target program form, memory management, instruction selection, register allocation, evaluation order, code-generation approach.
  • Target forms: absolute machine code (fixed memory location, run immediately) · relocatable machine code (separate compilation, then link/load) · assembly language (easier, symbolic).
  • Evaluation order affects efficiency: reordering independent computations for a+b-(c+d)*e saves a load/store and a register.
  • Target machine model: byte-addressable, 4-byte words, registers R0…Rn−1, two-address instructions op source, destination (MOV, ADD, SUB…).

  • Cost of an instruction = 1 + costs of its operands (register = 0, memory/constant = 1). Program cost = sum. E.g. MOV R0,R1 = 1; MOV R0,M = 2; SUB 4(R0),*12(R1) = 3.
  • Example a = b + c: MOV b,R0; ADD c,R0; MOV R0,a costs 6, but if R0, R1, R2 already hold the addresses of a, b, c then MOV *R1,*R0; ADD *R2,*R0 costs 2 (keeping values in registers pays off).
