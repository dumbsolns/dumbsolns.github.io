Question 1: short theory answers

Deep dives: summary · LL(1) · LR · SDT/TAC · PDA · automata · CFG/CNF · RE · DFA design

Language processing system Sp25

Source (high-level) → preprocessor (macros, file inclusion) → compiler (to assembly) → assembler (to relocatable object code) → linker (merges object files, resolves external references) → loader (loads the executable into memory, sets registers, starts execution). An interpreter instead translates and runs one statement at a time. Cross-compilers target a different platform; source-to-source compilers emit another high-level language.

Linker and loader; why relocatable code Sp24: the assembler cannot know final memory addresses or where other modules live, so it emits relocatable code with relative addresses. The linker combines modules and fixes references; the loader assigns actual addresses.

Block diagram and components of a compiler Fa24, Sp24, Sp23

chars → Lexical → tokens → Syntax → parse tree → Semantic (SDT) → annotated tree
      → Intermediate code gen → 3-address code → Optimizer → Code generator → target
      (Symbol table + Error handler interact with every phase)
  • Lexical: groups characters into lexemes/tokens (RE → NFA → DFA, tool FLEX), removes whitespace and comments.
  • Syntax: checks tokens against a CFG, builds parse tree (LL, LR parsers; tool Bison).
  • Semantic: type checking, scope resolution; attaches attributes (SDT).
  • Intermediate code: machine-independent 3-address code. Optimizer: faster/smaller code, same meaning. Code generator: target code, register allocation, instruction selection.
  • Front end = analysis (lexical, syntax, semantic); back end = synthesis (optimization, code generation). Analysis phase Fa23 reads the source, splits it into tokens, builds an intermediate representation and the symbol table, and reports syntax and semantic errors.

Intermediate code, 3-address code and portability Sp25, Fa24 [book]

Intermediate code sits between source and machine code so that one front end can serve many back ends (N languages + M machines instead of N×M compilers). Three-address code has at most one operator on the right (t1 = b * c), uses compiler-made temporaries, and is machine-independent, so only the code generator is rewritten per architecture, and the optimizer works once on the IR. Representations (Dragon Book §6.2.2): quadruples (op, arg1, arg2, result): easy to reorder, so good for optimization, but more space; triples (op, arg1, arg2), compact but results are referenced by position, so moving code is hard; indirect triples (a list of pointers to triples): reordering is cheap, at the cost of an extra indirection.

Lexical errors and recovery Sp25

A lexical error is a character sequence matching no token pattern (illegal character, misspelled keyword/identifier, e.g. @var). The lexer reports it with line number, then recovers by: (1) panic mode: delete successive characters until a valid token starts (int x@@ = 5; drops @@); (2) delete/insert/replace one character or transpose two adjacent characters (whlie → while) to form a valid token.

SDT, synthesized vs inherited attributes Sp25

Syntax-directed translation augments the grammar with attributes and semantic rules/actions run as productions are reduced; the result is an annotated parse tree (CFG + semantic rules = SDD). A synthesized attribute is computed from the children (S→ABC: S gets values from A, B, C), as in E → E+T { E.val = E.val + T.val }; S-attributed SDTs use only these (bottom-up). An inherited attribute is taken from the parent and/or siblings (e.g. the type passed down in a declaration T L to each identifier in L); L-attributed SDTs may use inherited attributes from the parent and left siblings only (top-down).

Ambiguity Sp25, Fa23, Sp23

A grammar is ambiguous if some string has two parse trees (equivalently, two leftmost or two rightmost derivations). Example: E → E+E | E*E | id on id+id*id gives two trees (+ at the root, or * at the root). Unambiguous version: E → E+T | T; T → T*F | F; F → (E) | id, one tree only, with * binding tighter. Problem: the parse tree determines meaning, so the same program could evaluate differently, and top-down parsers cannot choose a production. Removal: (1) disambiguating rules (precedence and associativity) without changing the grammar, or (2) rewrite the grammar with one non-terminal per precedence level. (Dangling else needs matching each else with the nearest then.)

Parsing phase, algorithms, top-down vs bottom-up Sp25, Fa24, Fa23

The parser takes tokens from the lexer, checks that they are generated by the CFG, builds the parse tree/AST, reports and recovers from syntax errors. It cannot catch re-declarations, uninitialized use or type mismatch (semantic phase). Top-down (recursive descent with backtracking, predictive LL(1)): builds the tree from the start symbol using leftmost derivation; easy to write by hand, but needs no left recursion or left factoring and handles a smaller grammar class. Bottom-up (shift-reduce: LR(0), SLR, LALR, canonical LR): builds from the leaves, reducing to the start symbol (reverse rightmost derivation); handles larger grammar classes and left recursion, so it is the one used in real tools such as Bison, but tables are large and hard to build by hand. [book] Dragon Book §4.4–4.5.

Shift-reduce conflicts Sp24, Sp23 [book]

A shift-reduce parser shifts input onto a stack and reduces a handle to a non-terminal. Shift/reduce conflict: a state can either shift the next token or reduce. Reduce/reduce conflict: two different reductions apply. Causes: ambiguous grammar, or lookahead too weak (LR(0) uses none). Example: in LR(0) for E → T | T*F … the state {E→T•, T→T•*F} has both reduce and shift on *. SLR fixes it by reducing only on FOLLOW(E) = {$, +, )}. Reduce/reduce: state with A→d• and B→d•.

LL(1) grammars and the table algorithm Sp24, Fa23

Conditions: no left recursion, no left factoring, unambiguous; for each A→α|β: FIRST(α)∩FIRST(β)=∅; at most one alternative derives ε, and if β⇒*ε then FIRST(α)∩FOLLOW(A)=∅. Algorithm: compute FIRST and FOLLOW; for each A→α put it in M[A,a] for a∈FIRST(α); if ε∈FIRST(α), put it in M[A,b] for each b∈FOLLOW(A). A cell with two entries means the grammar is not LL(1); the fix is rewriting (remove left recursion/factoring) or using a stronger parser. Impact: the table makes each step a lookup, so no backtracking, giving linear-time predictive parsing.

SLR table steps Sp24 [book]

  1. Augment the grammar (S′→S). 2. Build the canonical LR(0) item sets with closure and goto. 3. Shift: if item A→α•aβ in Ii and goto(Ii,a)=Ij, ACTION[i,a]=shift j. 4. Reduce: if A→α• in Ii, ACTION[i,a]=reduce A→α for every a∈FOLLOW(A). 5. S′→S• gives accept on $. 6. goto(Ii,A)=Ij fills GOTO. 7. Empty cells are errors; any multiple entry means the grammar is not SLR.

Formal definitions: DFA, NFA, ε-NFA, PDA Sp25; extended δ: Fa24, Fa23

  • DFA (Q,Σ,δ,q₀,F), δ:Q×Σ→Q. Example: strings ending in 01 (3 states). + Simple, fast, easy to implement as a table; − can be large, harder to design.
  • NFA same tuple with δ:Q×Σ→2Q; accepts if some path ends in F. Example: ends in 01 with 3 states. + Easy to design and small; − must be simulated or converted (up to 2ⁿ DFA states).
  • ε-NFA δ:Q×(Σ∪{ε})→2Q; ε-moves need no input; uses ECLOSE. + Easiest to build from regular expressions (union, concatenation, star); − needs ε-closure computation.
  • PDA (Q,Σ,Γ,δ,q₀,Z,F): finite control plus a stack. Example: aⁿbⁿ. + Recognizes all context-free languages (nesting, balanced brackets) that finite automata cannot; − nondeterministic PDA are more powerful than DPDA, and parsing is costlier. Also not enough for context-sensitive structure.
  • Extended transition function: DFA: δ̂(q,ε)=q, δ̂(q,xa)=δ(δ̂(q,x),a). NFA: δ̂(q,xa)=∪ δ(p,a) over p∈δ̂(q,x). Language: DFA δ̂(q₀,w)∈F; NFA δ̂(q₀,w)∩F≠∅. Example for the NFA ending in 01: δ̂(q₀,101) = {q₀,q₁} then {q₀,q₂} contains q₂ → accept.

Other short ones

  • CFG Sp24: G=(V,T,P,S); called context-free because the left side of every production is a single variable, so replacing it never depends on its surrounding context.
  • Natural vs formal language Fa24, Fa23: natural languages evolve and are ambiguous (“I saw the man with the telescope”); formal languages are strictly defined by a grammar, so every compiler phase can decide validity mechanically. Example: a+b*c must have exactly one meaning. Formal languages specify tokens (regular expressions) and syntax (CFG).
  • Symbol, alphabet, string Fa24: symbol = undefined atom; alphabet Σ = finite non-empty set of symbols ({0,1}); string = finite sequence of symbols over Σ (0110, ε); language = subset of Σ*.
  • Left recursion elimination Sp23: A → Aα | β becomes A → βA′; A′ → αA′ | ε. Example E → E+T | T becomes E → TE′; E′ → +TE′ | ε.
  • DFA in compiler design Sp23: the lexer is a DFA (from the token REs): e.g. identifier letter(letter|digit)* as states start → in-id (accepting, loops on letter/digit).
  • Lexical analysis illustrated Sp23: see Q3 (lexical analysis of a code snippet).

  • (0|1)*10 (and (0|1)*01 by swapping): A–1→B, A–0→A; B–0→C*, B–1→B; C–1→B, C–0→A.

  • ab(a|b)*ab (minimal): p0–a→p1–b→p2; p2: a→p3, b→p2; p3: a→p3, b→p4*; p4: a→p3, b→p2; dead state for a wrong start. Shortest string abab. (The state after the prefix and the state “last symbol b” behave identically, so one state p2 serves both.)
  • 01(0|1)*01 (minimal): p0–0→p1–1→p2; p2: 0→p3, 1→p2; p3: 0→p3, 1→p4*; p4: 0→p3, 1→p2; dead state elsewhere. Shortest string 0101.

Cases→ Case Cases | Case
Case → case num : Stmts break ;
Def  → default : Stmts break ; | ε

S    → do { Stmts } while ( Cond ) ;
Stmts→ Stmt Stmts | ε
Stmt → id = Expr ; | S
